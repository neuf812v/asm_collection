# ESP32-C3: запуск bare-metal асемблерної програми (RISC-V)

> Документ описує повний шлях налагодження «голої» асемблерної програми
> (blink на GPIO2) для **ESP32-C3-DevKitM-1**: що було не так, як зробити
> правильно, і як **не** треба. Включає повний флоу від подачі живлення до
> старту користувацького коду.
>
> Підсумок одним реченням: **для чистого bare-metal на ESP32-C3 не треба
> намагатися «подружитися» з ESP-IDF-бутлоадером — треба використати
> Direct Boot і вимкнути всі сторожові таймери, включно з Super WDT.**

---

## 1. Контекст і мета

Мета — запустити **повністю самостійну** (standalone) асемблерну програму на
RISC-V ядрі ESP32-C3, **без** ESP-IDF, FreeRTOS чи будь-якого runtime. Програма
проста: блимати світлодіодом на GPIO2 з частотою ~1 Гц.

Початкова (хибна) ідея була: взяти готовий **2-й ступінь бутлоадера**
(`bootloader.bin` з сусіднього PlatformIO-проєкту WS2812, ESP-IDF 5.5.3),
прошити свою програму як «застосунок» на `0x10000`, а бутлоадер нехай її
завантажить. Саме цей підхід і не спрацював — нижче детально чому.

---

## 2. Повний флоу завантаження ESP32-C3 (від живлення до коду)

```
┌──────────────────────────────────────────────────────────────────────┐
│ 1. POWER-ON / RESET                                                    │
│    Подається живлення → апаратний reset → старт ядра RISC-V.           │
└──────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────────────────────────────────────────────────────────────┐
│ 2. ROM BOOTLOADER (1-й ступінь, «зашитий» у кремній, незмінний)        │
│    - Читає strapping-піни (GPIO9 = BOOT, GPIO8) → визначає режим:      │
│        • SPI Flash Boot (звичайний)                                    │
│        • Download Boot (прошивка через UART/USB)                       │
│    - Друкує банер у UART0:                                             │
│        ESP-ROM:esp32c3-api1-20210207                                  │
│        rst:0x.. (причина скидання), boot:0x.. (режим)                  │
│    - У режимі SPI Flash Boot читає ПЕРШІ БАЙТИ флешу за адресою 0x0.   │
└──────────────────────────────────────────────────────────────────────┘
                                  │
                  ┌───────────────┴────────────────┐
                  ▼                                 ▼
┌──────────────────────────────┐   ┌──────────────────────────────────────┐
│ 2a. flash[0] == 0xE9          │   │ 2b. flash[0] != 0xE9                  │
│     («магія» ESP-образу)      │   │     ТА перші 8 байтів =               │
│     → це валідний образ       │   │     0xAEDB041D, 0xAEDB041D            │
│       2-го ступеня → ROM      │   │     → DIRECT BOOT                     │
│       завантажує його в RAM   │   │     ROM мапить весь флеш на           │
│       і стрибає у нього.      │   │     0x42000000 і стрибає на          │
│                               │   │     offset 8 → 0x42000008.           │
│   (ШЛЯХ, ЯКИЙ НЕ СПРАЦЮВАВ)   │   │   (ШЛЯХ, ЯКИЙ СПРАЦЮВАВ)             │
└──────────────────────────────┘   └──────────────────────────────────────┘
            │                                       │
            ▼                                       ▼
┌──────────────────────────────┐   ┌──────────────────────────────────────┐
│ 3a. 2-Й СТУПІНЬ (ESP-IDF)     │   │ 3b. НАШ КОД одразу                    │
│  - перевіряє таблицю розділів │   │  - виконується XIP прямо з флешу      │
│  - перевіряє esp_app_desc     │   │    (memory-mapped на 0x42000000)      │
│    (efuse rev і т.д.)         │   │  - _start: вимикаємо WDT,             │
│  - завантажує сегменти app    │   │    налаштовуємо стек, BSS,            │
│  - "Disabling RNG..."         │   │    викликаємо app_main                │
│  - КОНФІГУРУЄ Cache MMU під   │   │                                       │
│    DROM/IROM застосунку  ←←←  │   │  ✓ Жодного бутлоадера між ROM         │
│    тут падає abort()!         │   │    і нашим кодом.                     │
│  - стрибок у app              │   │                                       │
└──────────────────────────────┘   └──────────────────────────────────────┘
```

Умови активації Direct Boot (усі виконуються на стоковому DevKit):
- **Secure Boot вимкнено**;
- efuse **`DIS_LEGACY_SPI_BOOT` (DIS_DIRECT_BOOT) не пропалений**;
- на `0x0` **немає валідного ESP-образу** (перший байт ≠ `0xE9`);
- кремній **ревізії ≥ 3** (наш чіп — `v0.4`, тож підходить).

## 3. Що було не так (шлях через ESP-IDF-бутлоадер)

### 3.1. Симптом

У UART нескінченно повторювалося:

```
ESP-ROM:esp32c3-api1-20210207
Build:Feb  7 2021
rst:0x10 (RTCWDT_RTC_RST),boot:0xc (SPI_FAST_FLASH_BOOT)
I (xx) boot: ESP-IDF 5.5.3 2nd stage bootloader
...
I (xx) esp_image: segment 0: paddr=00010020 vaddr=3c010020 size=00100h ( 256) map
I (xx) esp_image: segment 1: paddr=00010128 vaddr=4037c000 size=000d8h ( 216) load
I (xx) boot: Loaded app from partition at offset 0x10000
I (xx) boot: Disabling RNG early entropy source...
abort() was called at PC 0x403d0eef        ← аvaria
```

Образ **приймався** бутлоадером (сегменти завантажувались), але одразу після
`"Disabling RNG early entropy source..."` стрілявся `abort()`, і чіп ішов у
reset-петлю (`RTCWDT_RTC_RST` → знову boot → знову abort).

### 3.2. Хибний діагноз, якого слід уникати

> «`abort()` — це функція runtime, отже падає ВАШ код / ваш app_main / ви не
> погодували watchdog».

Це **неправильно**. Доказ — арифметика адрес із самого логу.

З першого рядка логу видно, **куди ROM завантажив сам бутлоадер**:

```
load:0x3fcd5820,len:0x155c     ← DRAM бутлоадера
load:0x403cbf10,len:0xc84      ← IRAM бутлоадера
load:0x403ce710,len:0x2fa4     ← IRAM бутлоадера → кінець ≈ 0x403D16B4
entry 0x403cbf1a               ← точка входу бутлоадера
```

Отже **код бутлоадера** займає діапазон `0x403CBF10 – 0x403D16B4`.

- `abort() at PC 0x403d0eef` → `0x403CBF10 ≤ 0x403D0EEF < 0x403D16B4`
  → **adресa всередині бутлоадера**, а не нашого коду.
- Наш застосунок мав `entry = 0x4037C000`. PC `0x403d0eef` не має до нього
  жодного стосунку — **наш код навіть не починав виконуватися**.
- `addr2line` по нашому `.elf` для цієї адреси повернув би порожнечу — цієї
  адреси в нашому бінарнику немає.
- `"Disabling RNG early entropy source..."` — це **повідомлення самого
  бутлоадера** на самому кінці, перед стрибком у застосунок. abort стається
  **між** ним і стрибком — фізично в коді бутлоадера.

`abort()` є **і в бутлоадері** (це звичайна C-функція ESP-IDF, вкомпільована в
нього). Watchdog тут ні до чого.

### 3.3. Справжня причина (реверс бутлоадера)

Дизасемблювання `bootloader.bin` показало: усі шляхи до abort у функції
`0x403d0ed4` (налаштування Cache MMU, аналог `Cache_..._MMU_Set`) ведуть в одну
інструкцію `jal <abort>` за адресою `0x403d0eee` (звідси PC `0x403d0eef`).

Ця функція перевіряє параметри сегмента для кеш-мапінгу:

```
Check 1 (вирівнювання):  (vaddr | paddr) & 0xFFFF == 0   інакше → abort
Check 2 (розмір/межі):   paddr + size - 1 < 0x01000000   інакше → abort
```

У фінальній фазі `unpack_load_app` бутлоадер **безумовно** конфігурує
DCache (DROM) та ICache (IROM) на основі сегментів застосунку. Якщо застосунок
**не має** DROM/IROM-сегмента (наш суто-IRAM blink), то акумульований
`size = 0`, і Check 2 рахує `0 + 0 - 1 = 0xFFFFFFFF ≥ 0x01000000` → **abort**.

Спроби «догодити» бутлоадеру **не дали результату**:
- ❌ суто-IRAM розкладка → abort (немає DROM/IROM → size=0);
- ❌ IROM-сегмент з app_desc (vaddr `0x42000020`) → abort;
- ❌ DROM-сегмент з app_desc (vaddr `0x3c010020`) → проходить Check 1/2, але
  спотикається на внутрішній перевірці мапінгу сторінок далі.

**Висновок:** цей конкретний ESP-IDF-бутлоадер несумісний із рукописними
bare-metal образами, і боротьба з ним не має навчальної цінності. Треба інший
підхід.

## 4. Як зробити правильно — Direct Boot

ROM ESP32-C3 уміє запускати код **прямо з флешу**, повністю минаючи 2-й ступінь.
Це і є «чистий standalone»: ні бутлоадера, ні runtime, ні `abort()` — нема кому
його викликати.

### 4.1. Формат образу

| Зсув у флеші | Вміст | Призначення |
|---|---|---|
| `0x0` | `1d 04 db ae` (`0xAEDB041D`) | магія Direct Boot, копія 1 |
| `0x4` | `1d 04 db ae` (`0xAEDB041D`) | магія Direct Boot, копія 2 |
| `0x8` | `_start` (наш код) | ROM стрибає сюди (vaddr `0x42000008`) |
| `0x8+` | `.text` / `.rodata` | виконується/читається XIP з флешу |

Перший байт образу — `0x1D` (не `0xE9`), тому ROM **не** вважає його ESP-образом
і йде у гілку Direct Boot, де бачить магію.

### 4.2. Linker script (`link.ld`)

Ключове: код лінкується на `0x42000000` (memory-mapped флеш), BSS і стек — у
DRAM (SRAM). Жодних DROM/IROM-сегментів у форматі ESP-образу.

```ld
ENTRY(_start)
MEMORY
{
    flash (RX) : ORIGIN = 0x42000000, LENGTH = 0x400000   /* XIP-флеш */
    dram  (RW) : ORIGIN = 0x3FC80000, LENGTH = 0x50000    /* SRAM */
}
SECTIONS
{
    .text :
    {
        *(.text.entry)   /* магія + _start → _start лягає на 0x42000008 */
        *(.text*)
        *(.rodata*)
    } > flash

    .bss (NOLOAD) :
    {
        _bss_start = .;
        *(.bss*) *(COMMON)
        _bss_end = .;
    } > dram

    _stack_top = ORIGIN(dram) + LENGTH(dram);

    /DISCARD/ : { *(.comment) *(.riscv.attributes) *(.eh_frame*) }
}
```

Чому `.bss` як `NOLOAD`: інакше `objcopy -O binary` спробував би почати бінарник
з найнижчої адреси секції (DRAM `0x3FC80000` < флеш `0x42000000`) і створив би
гігантський файл із величезним «провалом». `NOLOAD` виключає `.bss` з файлу.
Секції `.data` ми взагалі не маємо (blink використовує лише immediate-значення),
тож копіювати initialized-data з флешу в RAM не потрібно.

### 4.3. Стартовий код (`startup.S`) — магія + ініціалізація

```asm
    .section .text.entry, "ax"

    # ── Магія Direct Boot (її читає ROM на flash 0x0) ──
    # Дві копії 0xaedb041d займають байти 0..7; _start іде з offset 8.
_magic:
    .word   0xAEDB041D
    .word   0xAEDB041D

    .global  _start
_start:
    # 1..3: вимкнути TIMG0 WDT, TIMG1 WDT, RTC WDT
    #        (ключ розблокування 0x50D83AA1 у *_WDTWPROTECT, потім 0 у *_WDTCONFIG0)
    # 3b:   вимкнути Super WDT (auto-feed) — див. розділ 4.4
    # 4:    la sp, _stack_top
    # 5:    обнулити .bss (_bss_start.._bss_end)
    # 6:    call app_main
    # .hang: j .hang
```

### 4.4. Обовʼязково: вимкнути Super Watchdog (SWD)

Після переходу на Direct Boot abort зник, але зʼявилася **нова** reset-петля:

```
rst:0x12 (SUPER_WDT_RST)
```

**Super Watchdog** — окремий сторожовий таймер у RTC, який **не** покривається
регістрами TIMG/RTC WDT. У direct boot його ніхто не вимикає, і він скидає чіп
приблизно раз на секунду. Послідовність вимкнення (метод
`bootloader_super_wdt_auto_feed` з ESP-IDF) — розблокувати, увімкнути авто-feed,
заблокувати:

```asm
    # RTC_CNTL_SWD_WPROTECT_REG = 0x600080B0, ключ = 0x8F1D312A
    # RTC_CNTL_SWD_CONF_REG     = 0x600080AC, біт AUTO_FEED_EN = BIT(31)
    li   t0, RTC_CNTL_SWD_WPROTECT_REG   # розблокувати
    li   t1, SWD_WRITE_PROTECT_KEY       # 0x8F1D312A
    sw   t1, 0(t0)
    li   t0, RTC_CNTL_SWD_CONF_REG       # виставити AUTO_FEED_EN (біт 31)
    lw   t1, 0(t0)
    li   t2, SWD_AUTO_FEED_EN            # (1 << 31)
    or   t1, t1, t2
    sw   t1, 0(t0)
    li   t0, RTC_CNTL_SWD_WPROTECT_REG   # заблокувати назад
    sw   zero, 0(t0)
```

### 4.5. Збірка та прошивка (`Makefile`)

Не `esptool elf2image` (він робить ESP-образ із заголовком `0xE9`), а **raw
бінарник** через `objcopy`, і прошивка на `0x0` замість бутлоадера:

```makefile
blink.bin: blink.elf
	$(OBJCOPY) -O binary $< $@          # RAW-образ, без ESP-заголовка

flash: blink.bin
	$(PYTHON) -m esptool --chip esp32c3 -p $(PORT) \
		--before default_reset --after hard_reset write_flash \
		0x0 blink.bin                    # на 0x0, БЕЗ бутлоадера й таблиці розділів

erase:
	$(PYTHON) -m esptool --chip esp32c3 -p $(PORT) erase_flash
```

Таблиця розділів (`0x8000`) і застосунок (`0x10000`) у Direct Boot **не
потрібні** — ROM їх ігнорує.

## 5. Чек-ліст «як НЕ треба»

- ❌ **Не** намагатися завантажити рукописний bare-metal образ через готовий
  ESP-IDF 2-й ступінь — він безумовно конфігурує Cache MMU під DROM/IROM
  застосунку і падає в `abort()` ще до вашого коду.
- ❌ **Не** довіряти діагнозу «`abort()` → це ваш код/runtime». Перевіряйте, у
  чий діапазон адрес потрапляє PC (порівняйте з `load:`/`entry` бутлоадера в
  логу). Тут `0x403d0eef` — це **бутлоадер**.
- ❌ **Не** додавати `esp_app_desc_t` й гратися з розкладкою IROM/DROM заради
  бутлоадера — у Direct Boot це зайве і все одно не лікує abort.
- ❌ **Не** забувати про **Super WDT** — звичайного вимкнення TIMG/RTC WDT
  недостатньо (інакше `rst:0x12 SUPER_WDT_RST`).
- ❌ **Не** використовувати `esptool elf2image` для Direct Boot — потрібен
  **raw** бінарник (`objcopy -O binary`), що починається з магії, а не з `0xE9`.
- ❌ **Не** залишати `.data`/DRAM-секції як loadable у linker script без
  `NOLOAD` — `objcopy -O binary` створить величезний файл.

## 6. Чек-ліст «як треба»

- ✅ Перші 8 байтів образу = `0xAEDB041D` двічі; `_start` одразу за ними
  (offset 8 → vaddr `0x42000008`).
- ✅ Код лінкується на `0x42000000` (XIP-флеш), стек і `.bss` — у DRAM.
- ✅ У `_start`: вимкнути **TIMG0, TIMG1, RTC і Super** WDT → налаштувати стек
  → обнулити `.bss` → викликати `app_main`.
- ✅ Збирати `objcopy -O binary`, прошивати raw на `0x0`.
- ✅ Перевірити, що `flash[0] != 0xE9` і магія на місці перед прошивкою.

## 7. Фінальна структура проєкту `RISC-V/blink`

| Файл | Призначення |
|---|---|
| `link.ld` | XIP-флеш `0x42000000`, BSS+стек у DRAM, `.bss` як `NOLOAD` |
| `src/startup.S` | магія Direct Boot + вимкнення 4× WDT + стек + BSS + `app_main` |
| `src/blink.S` | IO_MUX GPIO2 (MCU_SEL=1), enable output, цикл ON/затримка/OFF/затримка |
| `src/registers.h` | адреси регістрів, ключі WDT/SWD, `DELAY_CYCLES`, `BLINK_*` |
| `Makefile` | `objcopy -O binary`, ціль `flash` (0x0), `erase`, `dis` |

### Використані регістри

| Регістр | Адреса | Призначення |
|---|---|---|
| `IO_MUX_GPIO2_REG` | `0x6000900C` | маршрутизація піна (MCU_SEL=1 → GPIO-матриця) |
| `GPIO_ENABLE_W1TS_REG` | (з `gpio_reg.h`) | увімкнути вихід GPIO2 |
| `GPIO_OUT_W1TS_REG` / `_W1TC_REG` | (з `gpio_reg.h`) | встановити / скинути рівень |
| `RTC_CNTL_SWD_WPROTECT_REG` | `0x600080B0` | розблокування Super WDT (ключ `0x8F1D312A`) |
| `RTC_CNTL_SWD_CONF_REG` | `0x600080AC` | `AUTO_FEED_EN` = біт 31 |
| ключ WDT (TIMG/RTC) | `0x50D83AA1` | розблокування WDTWPROTECT |

## 8. Прошивка та перевірка

```powershell
cd RISC-V/blink
mingw32-make                 # збірка → blink.bin (raw, починається з 1d04dbae…)
mingw32-make flash PORT=COM16
```

Якщо `esptool` пише **«No serial data received»** — плата не зайшла в Download
mode. Тоді або повторити (CH340K інколи не входить у sync з першого разу), або
ввести вручну: **тримати BOOT → коротко RST → відпустити BOOT**. Альтернатива —
прошивати через рідний USB-Serial-JTAG (інший COM-порт, «USB Serial Device»).

**Результат (підтверджено логічним аналізатором на GPIO2):**
- чистий меандр, **Duty 50%**, період **1.000 с**, частота **≈1 Гц**;
- жодного `abort()`, жодної reset-петлі — чіп стабільний.

## 9. Нюанс таймінгів і подальші кроки

У Direct Boot CPU стартує на **дефолтній ROM-частоті** (не 160 МГц), і код
виконується XIP з флешу (кеш + такти очікування). Виміряно: цикл затримки

```asm
    li   t2, DELAY_CYCLES
.delay:
    addi t2, t2, -1
    bnez t2, .delay
```

дає **≈200 нс на ітерацію**. Тому:
- `DELAY_CYCLES = 40 000 000` → півперіод 8.0 с (період 16 с);
- `DELAY_CYCLES = 2 500 000` → півперіод 0.5 с (період **1.000 с**, ✓ обрано).

**Подальші можливі кроки:**
1. Явно налаштувати CPU PLL на 160 МГц для детермінованих таймінгів (зараз —
   ROM-дефолт + XIP).
2. Власний вивід у UART (без runtime) для відладки.
3. Перенести цей самий Direct-Boot-каркас на проєкт WS2812 (GPIO8).
